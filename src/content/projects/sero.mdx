A collaborative bill-splitting application for shared living situations where groceries and common expenses need regular distribution. Instead of one person manually itemizing a receipt and chasing everyone for their share, Sero distributes the work — the uploader snaps a photo, OCR extracts the line items, and each roommate claims what they bought from their own phone.

The interesting engineering isn't in the UX. It's in the backend pipeline that turns an image into structured data, the abstractions that let the same code run locally and in production against different infrastructure, and the serverless AWS topology that hosts it all.

## Async OCR Pipeline

Receipt parsing is offloaded to a decoupled worker process so the upload API returns immediately. The flow:

- **Upload** — Client POSTs the receipt image; the API stores it in S3 (MinIO locally, AWS S3 in prod), creates an OCRJob record in Postgres, and publishes a job message to a queue.
- **Worker** — A separate worker process consumes jobs, downloads the image, calls the OCR provider, normalizes the response, and writes parsed line items back to Postgres.
- **Error handling** — `OCRPermanentError` (bad input, wrong provider) routes to the dead-letter queue. `OCRTransientError` (network, timeout) retries with backoff.

## Broker-Agnostic Queue Abstraction

Local development uses RabbitMQ. Production uses SQS. The worker code doesn't know the difference — both brokers sit behind a common `publish_ocr_job` interface, and the correct backend is selected at startup from environment config. The same worker binary runs in both environments with no code changes.

## Provider Abstraction

OCR providers implement a Protocol interface, with normalization and reconciliation layers between the raw response and the domain model. The current backend is Mindee's financial document API, but swapping providers requires no changes to business logic — only a config flag.

## Bill Lifecycle

Bills progress through a state machine enforced at the API layer:

- **DRAFT** — Receipt uploaded, OCR parsing in flight.
- **OPEN** — Claiming window active; participants tap line items to claim them.
- **LOCKED** — Claiming window closed; final amounts computed.
- **SETTLED** — All participants have acknowledged their share.

Transitions are driven by timed claim windows and per-participant submission tracking. Illegal transitions are rejected at the API boundary.

## Infrastructure

The production stack is fully serverless, provisioned end-to-end with AWS CDK:

- **Compute** — Three Lambda functions: the API (FastAPI via Mangum adapter), the SQS-triggered OCR worker, and a one-shot Alembic migrator invoked on deploy.
- **Database** — Aurora PostgreSQL Serverless behind an RDS Proxy. The proxy pools and multiplexes connections so Lambda's bursty invocation pattern doesn't exhaust Postgres connection limits under concurrent cold-starts.
- **Queue** — SQS with a dead-letter queue (14-day retention, 3 receive attempts) and batch-item failure reporting from the Lambda event source.
- **Networking** — 3-tier VPC. Aurora lives in an isolated subnet unreachable from the public internet. Lambdas sit in private subnets with egress via NAT. Security groups chain explicitly: Lambda SG → RDS Proxy SG → DB SG.
- **Secrets** — Database credentials, JWT signing keys, and provider API keys all live in AWS Secrets Manager, fetched at Lambda cold-start. Nothing baked into config.
- **Frontend delivery** — Static Expo web build served from S3 through CloudFront with Origin Access Identity. SPA fallback routes 403/404 responses to `index.html`.

## Auth

JWT-based authentication with short-lived access tokens and long-lived refresh tokens. Passwords hashed with Argon2 via passlib. Schema and migrations managed with SQLModel and Alembic.

## Local Development

The local stack is orchestrated as a 6-service Docker Compose setup: FastAPI backend, OCR worker, Postgres, RabbitMQ with management UI, MinIO as an S3-compatible store, and Adminer for database inspection. A `minio-init` container provisions the bucket and sets the ACL before workers start. Alembic migrations run on container startup before Uvicorn.

## Mobile Client

Built with Expo, React Native, and Expo Router — a single codebase that runs as a native iOS app, a native Android app, and an installable PWA on the web. React Query handles server state and cache invalidation; Zustand manages local UI state like unsaved claims and leave-guard prompts.

Designed the system end-to-end: the async OCR pipeline and its error taxonomy, the broker-agnostic queue abstraction that lets the same worker run against RabbitMQ or SQS, the OCR provider interface with its normalization and reconciliation layers, and the bill lifecycle state machine. Provisioned the AWS stack with CDK — Lambdas, Aurora Serverless behind RDS Proxy, the 3-tier VPC, Secrets Manager wiring, and CloudFront delivery — and built the cross-platform client in Expo.
