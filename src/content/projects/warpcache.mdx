WarpCache is a CUDA kernel study of decode attention, the step where a language model generates one token by reading every earlier token's keys and values from the KV cache. It asks two questions: does storing the cache in INT8 make decode faster, and how should the work be divided across the GPU? It pairs a readable PyTorch reference with a CUDA implementation, correctness tests, and Nsight Compute profiles. Built as a CS 259 class project, sized to the Qwen3-1.7B attention shape.

## Why Decode Attention Is Memory Bound

Each decode step does about 2 floating point operations per byte it reads from the cache. A GPU needs far more than that to be limited by arithmetic, so decode speed is set by how fast and how fully the kernel pulls the cache from memory. The cache is also large: sixteen requests with 16K tokens of history need 28 GiB in FP16, more than an RTX 3090 holds.

## Two Execution Paths

The kernel uses one 32-thread block per request, query head, and chunk. Each lane handles four of the 128 head dimensions, warp shuffles combine the dot products, and keys and values are read through a block table from the paged cache. INT8 values are dequantized as they load.

| Path | Behavior |
|---|---|
| **Path A** | One block covers the whole history and writes the final output. |
| **Path B** | The history is split into chunks, each with its own block. Blocks write partial softmax states that are merged afterward (Flash-Decoding style). |

At batch size 1, Path A launches only 16 blocks on a GPU with 82 SMs, so most of the chip sits idle. Path B fixes that by creating more blocks, at the cost of a merge.

## Results

Measured on one RTX 3090 at batch sizes 1, 4, and 16 and histories of 4K and 16K tokens:

- **Split-KV wins everywhere.** Path B at 128 chunks is 3.9x to 50x faster than Path A. At batch 1 with a 16K history, decode drops from 8.1 ms to 162 µs.
- **INT8 halves memory, not latency.** INT8 storage takes 2,112 bytes per token per layer against 4,096 for FP16, but decode time barely moves. Nsight Compute showed the kernel is occupancy bound, not bandwidth bound, so fewer bytes do not buy speed.
- **K outliers hurt INT8.** Outlier channels in real model keys make per-token INT8 lossy. Static K smoothing cut attention-output error from 6.1% to 1.8%.
- **One good configuration was enough.** A hand-set selector of 128 chunks lands within 3.8% of the best chunk count in all 24 measured cases.
- **FlashAttention is still faster.** PyTorch SDPA beats Path B by 1.5x to 1.65x, likely because it keeps more bytes in flight per block. WarpCache does not claim a speedup over PyTorch or a serving engine.
